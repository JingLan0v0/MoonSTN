# MoonSTN 后续优化路线

当前发布基线为 **0.2.26**，源码提交 `14c0af2`。当前通过验证的范围是
MoonBit JS 后端、Node CLI 和库 API，
Windows 与 Ubuntu 的 debug/release。工具链按 `toolchain.json` 固定。
后续以新版本的实际 Git 与发布状态更新基线。 [进展](progress.md) · [验收证据](acceptance.md)

## 收到「继续优化」时

1. 核对桌面当前仓库的分支、工作区、远端提交和注册表版本，保留用户改动及 Git 历史。
2. 优先处理可重放的错误结果、崩溃、资源越界或安装失败。其余时间从下表最早的待验证项开始，一轮完成一项。
3. 先记录基线输入、输出、预算和耗时，再决定是否改代码。性能收益不稳定且没有独立的正确性收益时，记录实测、结论和复现入口，撤去本轮候选并推进下一项。
4. 验收后更新本表状态和下一项，并在验收记录单独保存本轮证据。同步已验证提交，沿用现有发布授权与验收流程。

## 每轮验收

- **测量**使用同机、同工具链、同构建模式、同输入和预算。先核对输出等价，再交替运行基线与候选。保留各次样本、中位数、范围及可取到的峰值 RSS。注明计时包含哪些阶段，分别报告 CLI、库内与编译数据中的实测项。性能结论同时涵盖目标负载、普通负载和受影响的边界。
- **正确性**保留精确整数、公开接口及可读字段、独立证书和安排核验。保持 `planned`、`unschedulable`、非法输入和 `limit_exceeded` 的区别。比较精确预算与差一单位、批处理失败项和随后正常项、失败后模型复用。
- **工程验收**运行 `moon fmt`、`node scripts/verify.mjs` 和 `./scripts/powershell-smoke.ps1`，检查生成接口。规划改动可将保存的基线 CLI 的绝对路径传给统一验证脚本，比较规划批次输出。记录实际源码 SHA、用例计数和对应的 Windows／Ubuntu CI。
- **需要发布时**在打包前对齐清单、库版本、CLI 与包内安装示例。检查实际 ZIP 文件和哈希，从干净解压目录验证。分别保存预检和正式发布回执，再从空缓存安装精确版本，运行公开 API 和失败恢复案例，核对公开下载及安装内容。 [发布流程](publishing.md)
